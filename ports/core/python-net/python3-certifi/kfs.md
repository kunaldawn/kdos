## About
certifi is a Python package whose only content is a CA bundle and two functions:
`certifi.where()` returns the bundle's path and `certifi.contents()` its text.
[python3-requests](#port-python3-requests) takes its trust anchors from there rather than asking
the system.

KDOS ships no copy of certifi's bundle. After the install, `build.sh` replaces
`certifi/cacert.pem` with a symbolic link to `/etc/ssl/cert.pem`, the file
[ca-certificates](#port-ca-certificates) writes, so Python code trusts exactly the roots
OpenSSL does, local roots included; see
[TLS trust anchors](../../../../docs/kdos/03-architecture/security-model.md#tls-trust-anchors).

## Flags
- `--no-build-isolation` — Build with the setuptools already installed in the build root
  (`requires = ["setuptools >= 42.0.0"]`) rather than one pip would fetch into a temporary
  environment; [python3-setuptools](#port-python3-setuptools) is in `depends`.

## Notes
`pem=$(echo …/python3*/site-packages/certifi/cacert.pem)` expands to the installed file only
when the glob matches exactly one path. With no match it stays the literal pattern, and with two
interpreter directories it becomes two paths in one word, and in both cases `test -f "$pem"`
fails the build instead of leaving the bundled copy in place.

The link points at a file no package owns: `/etc/ssl/cert.pem` is generated by
`update-ca-certificates`, which ca-certificates runs when it is installed and upgraded. Until
then the link dangles; ca-certificates is in `depends`. A local root added to
`/etc/ca-certificates/trust-source/anchors/` reaches Python only after
`update-ca-certificates` has run again.
