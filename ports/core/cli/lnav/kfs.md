## About
lnav, the Logfile Navigator, opens many log files at once and merges them into one view in time
order, recognising the common formats (syslog, web server access logs, JSON lines and more) so it
can colour, filter and jump between errors. Each recognised format is also a table, so a question
about the logs can be put to them in SQL, or in PRQL through the Rust extension. On KDOS it is the
tool for asking questions of this machine's own logs. The port installs `lnav` and a desktop entry
that opens it in a terminal as *Log Viewer*.

## Flags
- `--with-libarchive` — Open logs inside archives with [libarchive](#port-libarchive). It is
  configure's default; when the library is missing configure prints `no` and goes on without it.
- `--with-cargo` — Build the Rust extension, `src/third-party/lnav-rs-ext`, as a static library
  linked into `lnav`. It carries the PRQL compiler and lnav's other Rust code; without cargo, or
  with `--without-cargo`, lnav is built without them.
- `--disable-system-paths` — Add no extra search paths. By default configure appends
  `-I/opt/local/include` and `-I/usr/local/include` to `CPPFLAGS`, and `-L` for the `lib`, `lib64`
  and `lib/x86_64-linux-gnu` directories of `/opt/local`, `/usr/local`, `/usr` and `/` to `LDFLAGS`,
  wherever those directories exist.
- `ac_cv_path_RE2C_CMD=` — Pre-answer configure's search for `re2c` with nothing, so the
  scanners are built from the C++ files generated by `re2c` that ship in the source rather than
  regenerated. re2c is not in the tree.
- `ac_cv_path_CXXBRIDGE=` — The same for `cxxbridge`, the generator of the C++ side of the Rust
  extension's interface: the generated `lnav_rs_ext.cxx.hh` and `.cxx.cc` in the source are used
  as they are.

## Patches
- `lnav-tailer-static.patch` — lnav tails a file on a remote host (`lnav user@host:/var/log/syslog`) by copying a small helper, the tailer, over `ssh` and running it there. Upstream embeds `tailer.ape`, a prebuilt Actually Portable Executable checked into the source; the patch builds the tailer from `tailer.main.c` instead, as a static, stripped executable, `tailer.static`, and embeds that. The remote side then runs a binary built by this tree rather than one fetched with the source; being an ordinary static Linux ELF, it runs only on an x86-64 Linux remote.

## Notes
The Rust extension's crates come from a vendor bundle, `lnav-vendor-<version>.tar.xz`. Its
`vendordir = src/third-party/lnav-rs-ext` tells `ports/fetch` to run `cargo vendor` beside the
extension's manifest, and the bundle replaces both crates.io and the extension's one git
dependency, `log2src`, with the vendored copies. `build.sh` unpacks the bundle into `src/`, not
beside the manifest: the Makefile runs `cargo build --manifest-path …` from `src/`, and cargo finds
the bundle's `.cargo/config.toml` only by walking up from the directory it runs in, so a bundle
placed anywhere else leaves cargo trying to clone the git dependency in a build with no network.
See [Where the bundle goes](../../../../docs/kdos/05-developer/writing-ports.md#where-the-bundle-goes).

The source is GitHub's archive of the tag, which carries no `configure`, so `build.sh` runs
`./autogen.sh` first, with the `autoconf`, `automake` and `libtool` in `depends`. That also
regenerates `src/tailer/Makefile.in` from the patched `Makefile.am`, so the patch is applied before
it.
