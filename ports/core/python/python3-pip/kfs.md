## About

pip is Python's package installer. In KDOS it has two jobs. Recipes use it: almost every `python3-*`
port installs itself with `pip3 install --root="$PKG"`, from a source tree or from the port's vendor
bundle, and names `python3-pip` in its `depends`. And it supplies the pip that goes into a virtual
environment: the system's `site-packages` is kpkg's (see [Files kpkg keeps to
itself](https://github.com/kunaldawn/kdos/blob/main/docs/kdos/03-architecture/packaging.md#files-kpkg-keeps-to-itself)),
so Python software that is not a port is installed with `python3 -m venv`, and `venv` takes pip from
the wheel this package puts in `/usr/share/python-wheels`.

pip builds with the backend `flit_core`, and no pip exists yet to install itself with. `build.sh`
therefore runs pip from its own source tree (`PYTHONPATH=src python3 -m pip`) against the port's
vendor bundle, a second tarball holding the `flit_core` source distribution, which `ports/fetch`
made in advance so that the build needs no network; see
[Vendoring](https://github.com/kunaldawn/kdos/blob/main/docs/kdos/05-developer/writing-ports.md#vendoring).

## Flags

- `--no-index` — with `--find-links=vendor`: take every distribution from the unpacked bundle in
  `vendor/` and never contact a package index. The build runs offline.
- `--no-deps` — install pip alone and resolve no dependencies. pip has no run-time dependencies: the
  libraries it uses are vendored inside it, under `pip/_vendor`.
- `--ignore-installed` — never look at, or uninstall, a copy already installed in the build root.
  Without it, rebuilding pip over an installed pip would first remove the live one from the tree
  every later build uses; see [The three Python
  keys](https://github.com/kunaldawn/kdos/blob/main/docs/kdos/05-developer/writing-ports.md#the-three-python-keys).
  `testing/preflight.sh` refuses a `pip install --root` without it.
- `--root` — with `--prefix=/usr`: install under `$PKG`, as if `$PKG` were `/`, into `/usr`.
- `-w` — the directory `pip wheel` writes its wheel to: `/usr/share/python-wheels` inside `$PKG`,
  the directory [python3](#port-python3) is configured to give `ensurepip` (`--with-wheel-pkg-dir`).
  Without that wheel, `python3 -m venv` exits 1 and leaves an environment with no pip and no
  activate scripts.

## Notes

The wheel is followed by `chmod 644`. flit_core writes it through `tempfile.mkstemp`, which creates
the file with mode `0600`, and pip moves it into place unchanged; the package lint refuses a regular
file that not everyone can read, unless it is a listed credential.

pip's vendored `distlib` carries Windows launcher executables (`t32.exe`, `w64.exe` and the others),
which `build.sh` deletes from the package.

The bash completions are generated by running each installed `pip` command from `$PKG` with
`completion --bash`, with `PYTHONPATH` pointing at the staged `site-packages`, so the script for
`pip`, `pip3` and the versioned name is the one this pip writes.
