# The ISO

The last step of the build, `script/phases/70_image/110_iso.sh`, makes the file a user downloads and
writes to a stick: `build/iso-build/kdos.iso`. It gathers an ISO tree in four parts, the kernel and
the [initramfs]{.idx}, the root filesystem squashed into `system.sfs`, the [Limine]{.idx} boot menu, and then the
image itself, made by xorriso and then checked for what a stick needs to boot by [BIOS]{.idx} and by [UEFI]{.idx}. This chapter goes
through those parts in order, and ends with what the scripts do to make two builds of one tree give
the same image, and what they leave to the clock.

How the finished medium boots is described in
[Limine and the kernel command line](../../kdos/03-architecture/boot-and-init.md#limine-and-the-kernel-command-line)
and
[The live medium and persistence](../../kdos/03-architecture/boot-and-init.md#the-live-medium-and-persistence).

**Runs in:** the [chroot]{.idx}, as the last script step of `70_image`\
**Reads:** the root in `build/fs`, `build/initramfs.cpio.gz` from
[the initramfs step](090-initramfs.md), the recipe tree `105_ports.sh` staged in
`build/image-ports`, and with `KDOS_PACK_KDOS=1` the base pack in `build/kdos-base`\
**Writes:** the pseudo-file `build/sfs-var.pseudo`, the tree `build/iso_root/` and the image
`build/iso-build/kdos.iso`; in the root, [`/boot/initramfs.cpio.gz`]{.idx}

## The ISO tree

<!-- kfs:include script/phases/70_image/110_iso.sh lines=16-20 pin=a6b5b5aba652 -->

`build/iso_root` is made empty on every run. Everything the image holds is copied into it, and
xorriso turns that directory into the image at the end.

## The kernel and the initramfs

<!-- kfs:include script/phases/70_image/110_iso.sh lines=22-49 pin=bc2edeefdac4 -->

The kernel the [linux](#port-linux) port installed as `/boot/vmlinuz-kdos` is copied to
`boot/vmlinuz`, and the initramfs to `boot/initramfs.cpio.gz`. Both sit on the ISO9660 filesystem,
which Limine reads on BIOS and UEFI alike; see
[Where the kernel is kept](../../kdos/03-architecture/boot-and-init.md#where-the-kernel-is-kept).
Either file missing stops the step.

The initramfs is also copied into the root as `/boot/initramfs.cpio.gz`. The root is squashed in the
next part, so the copy is inside `system.sfs`, and a machine installed from the medium has it.
`/boot/initramfs-kdos.cpio.gz` is removed, for the reason the comment gives: it is the name the
`linux` package's `postinstall.sh` writes, and one left there from an earlier kernel would be chosen
ahead of this one.

## system.sfs

### The codec

<!-- kfs:include script/phases/70_image/110_iso.sh lines=51-67 pin=7ed20b612de4 -->

`KDOS_ISO_COMP` picks the compression of `system.sfs`, the image of the whole root. The `Makefile`
passes it into the build container, and `script/chroot/exec.sh` passes it on into the chroot. It
takes three forms:

| `KDOS_ISO_COMP` | mksquashfs gets | Use |
|:--|:--|:--|
| unset or empty | `-comp zstd -Xcompression-level 15` | the default |
| `zstd:1` to `zstd:22` | `-comp zstd -Xcompression-level <n>` | `zstd:3` for a quicker image on the rig |
| `xz` | `-comp xz` | xz at its defaults |

Any other value stops the step, so a mistyped codec cannot produce an image. The comment gives the
measurements behind level 15. For example:

```bash
make build KDOS_ISO_COMP=zstd:3 BUILD_ARGS="--phases 70_image"
```

### The squash

<!-- kfs:include script/phases/70_image/110_iso.sh lines=68-129 pin=3d1f9aced266 -->

First the step writes `build/sfs-var.pseudo`: a line `var/cache d 755 0 0` and one for `var/log`,
then one line for every directory an installed package claims below either, read from the `./var/…/`
lines of the package database's manifests, with each directory's parents added and the list
sorted so a parent comes before its children (mksquashfs refuses a definition whose parent does
not exist yet). Each carries the directory's mode, owner and group in the root, so samba's
`var/log/samba` comes out as `"var/log/samba" d 755 0 0`.

[mksquashfs](#port-squashfs-tools) reads the whole root, `/`, and writes `iso_root/system.sfs`.

`-noappend`
: Replace any `system.sfs` already there instead of adding to it.

`-comp …`
: The codec chosen above.

`-b 1M`
: 1 MiB blocks, the largest squashfs allows. The comment gives the trade: a smaller image, and a
  read of a small file that pulls a whole block off the medium.

`-p "proc d 555 0 0"` and the rest
: Pseudo-definitions: each makes a directory in the image with the given mode, owned by user 0 and
  group 0. They put back, empty, the directories the exclusions below take out, so that the booted
  system has its [mount points]{.idx term="mount point"}.

`-pf $VAR_PSEUDO`
: The same, read from the file written above: `/var/cache` and `/var/log` holding only the
  directories packages claim, empty. A daemon that makes its directory with one `mkdir` needs the
  parent, `smbd` and libvirt make none of theirs, and `kpkg check --all` reports a claimed
  directory that is absent as `missing`, which would fail a freshly booted image.

`-e proc sys dev tmp run mnt media var/cache var/log var/tmp/kdos-home build kdos ports`
: Leave these out. `proc`, `sys`, `dev`, `tmp` and `run` are the chroot's own mounts; `mnt` and
  `media` are mount points; `var/cache` and `var/log` hold the build's caches and logs;
  `var/tmp/kdos-home` is the build's home directory; `kdos` and `ports` are where the chroot mounts
  the repository, and `build` is a directory of that name in the root, if one is there. `-e` takes
  every argument after it as a name to exclude, so it is the last option on the line; the comment
  says what goes wrong otherwise.

### /ports

<!-- kfs:include script/phases/70_image/110_iso.sh lines=131-147 pin=9677abe74d62 -->

Every image carries the recipe tree at `/ports`, so that a booted machine can build from it. The
tree is not the chroot's `/ports`, which is the whole repository's `ports/` with every source in it.
`105_ports.sh` ([its chapter](105-ports.md)) stages a copy that holds recipes only, with KDOS's own
sources and the two books, in `build/image-ports/ports`, and stops if a file over 16 MB has found
its way in. When that staged tree has no `sources.idx`, this step stops before the append, naming
`105_ports.sh` as the step that did not run.

The second `mksquashfs` call names an existing image and no `-noappend`, so it appends: the staged
directory's entries are added at the image's root, in the codec and block size the image already
has. The check after it lists `ports/sources.idx` from the image with `unsquashfs -l` and stops the
step unless it is at `squashfs-root/ports/sources.idx`. An entry whose name is already in the image
would be appended under another name, `ports_1`, and that is the mistake the check catches.

### What else can go on the medium

<!-- kfs:include script/phases/70_image/110_iso.sh lines=149-168 pin=5370a3a7988c -->

`make build KDOS_PACK_KDOS=1` bakes a pack of the base system in `100_packs.sh`
([its chapter](100-packs.md)), and this block puts it on the medium as `packs/kdos.kpack`, beside
`system.sfs` rather than inside it. The test is the flag and the file together. `build/` is kept between builds, so
`100_packs.sh` also deletes `build/kdos-base` whenever the flag is off; between them, a pack reaches
the medium only on a build that asked for one. Packs are described in
[Packs and boxes](../../kdos/03-architecture/packs-and-boxes.md).

<!-- kfs:include script/phases/70_image/110_iso.sh lines=170-216 pin=6200efc5d054 -->

`make build KDOS_ISO_SOURCES=1` adds the build's own tree under `sources/` on the medium: `src`,
`script` and `fs`, every top-level entry of `ports/` but its dot-directories, and the `Makefile`
and `Dockerfile`. The script also names `CLAUDE.md`, but `make build` does not mount that file
into the build container, so a medium made by `make build` does not carry it. The
[binary host](010-binhost.md) goes along as `sources/binhost` whenever `build/binhost/PACKAGES`,
its index, exists: the test is the file, not the flag, so a binhost an earlier
`KDOS_MAKE_BINHOST=1` build left in `build/` is copied too. The `SOURCES` file is a stamp with the
number of recipes, the size, and the time of the copy. A booted medium sees it at `/mnt/iso/sources`, where
[kdos rebuild](../../kdos/04-programs/kdos-command.md#kdos-rebuild) looks for it.

## The boot menu

### Limine

<!-- kfs:include script/phases/70_image/110_iso.sh lines=218-243 pin=efb96b86a26a -->

[Limine](#port-limine) is the boot loader for both kinds of firmware. Its port installs its files in
`/usr/share/limine`, and five are copied:

| File | Goes to | Is |
|:--|:--|:--|
| `limine-bios.sys` | `boot/limine/` | the BIOS stage the boot code loads |
| `limine-bios-cd.bin` | `boot/limine/` | the El Torito boot image for BIOS |
| `limine-uefi-cd.bin` | `boot/limine/` | the El Torito boot image for UEFI, a FAT image with the EFI binaries in it |
| `BOOTX64.EFI` | `EFI/BOOT/` | the loader for 64-bit UEFI firmware |
| `BOOTIA32.EFI` | `EFI/BOOT/` | the loader for 32-bit UEFI firmware |

### The font

<!-- kfs:include script/phases/70_image/110_iso.sh lines=245-266 pin=1907da9164fb -->

The menu is drawn in Terminus `ter-i16n` from [terminus-font](#port-terminus-font), an 8x16 face.
Limine wants a [font]{.idx} as a bare bitmap of 256 glyphs in code page 437 order, which is not what a
console font file is, so the face is decompressed and converted by
`script/phases/70_image/psf2limine.py`. The script prints the size, `8x16`, which becomes
`term_font_size`. When the font is not installed, the menu is drawn in Limine's own.

`psf2limine.py` reads either version of the PSF format and writes the 256 glyphs Limine indexes by
CP437, taking each from the font's Unicode table:

<!-- kfs:include script/phases/70_image/psf2limine.py lines=14-25 pin=3841d4cb8170 -->

<!-- kfs:include script/phases/70_image/psf2limine.py lines=83-99 pin=e3a263474edd -->

Python's `cp437` codec decodes the first 32 slots and `0x7F` as control characters, so the script
carries its own table for them. Its two checks turn each silent failure into a stopped build:

<!-- kfs:include script/phases/70_image/psf2limine.py lines=108-117 pin=7af7e057c527 -->

<!-- kfs:include script/phases/70_image/psf2limine.py lines=141-151 pin=b9d8eef64a02 -->

A font that is not 8 dots wide is refused, because Limine would set it aside and draw in its own;
and a font that leaves any of the 256 slots without a glyph is refused, because it is not a CP437
face. A font with no Unicode table at all is copied in its own order.

The converter can be tried on its own, in the chroot:

```bash
zcat /usr/share/consolefonts/ter-i16n.psf.gz > /tmp/ter-i16n.psf
python3 /kdos/script/phases/70_image/psf2limine.py /tmp/ter-i16n.psf /tmp/font.bin
```

It prints `8x16` on standard output and a summary line, with the count of missing glyphs, on
standard error, and `/tmp/font.bin` is 256 glyphs of 16 bytes. Given the console's own
`ter-kdos16n.psf.gz` instead, it stops with a message naming how many glyphs are missing.

### The backdrop and the colours

<!-- kfs:include script/phases/70_image/110_iso.sh lines=268-310 pin=bc6af17e29d3 -->

The backdrop is `/usr/share/kdos/boot/kdos-backdrop.png`, or `kdos-banner.png` when there is no
backdrop; both are shipped by the `fs/` overlay. Without either the menu has a plain background.

Every other line of the look comes from `kdos-bootctl theme --print`, run with `KDOS_ACCENT` from
[`phase.env`]{.idx}. It prints the block `kcol_limine_conf()` in libkcolor writes, the same block the
installer writes onto an installed machine's ESP. The keys and why each has its value are in
[Why the plate is opaque](../../kdos/03-architecture/boot-and-init.md#why-the-plate-is-opaque) and
[The margin ceiling](../../kdos/03-architecture/boot-and-init.md#the-margin-ceiling); how to change
the accent is in
[Theming](../../kdos/02-user-guide/theming.md#the-boot-menu-the-splash-and-the-text-consoles).

### limine.conf

<!-- kfs:include script/phases/70_image/110_iso.sh lines=312-340 pin=315b5e610a4f -->

`timeout: 10` counts ten seconds down before `default_entry: 1`, the first entry, boots; any key
stops the count. The three entries boot the same kernel and initramfs, named by `boot():/`, the
volume the configuration file was read from. Their command lines differ:

- `KDOS Live` passes `quiet loglevel=3`.
- `KDOS Live (clean session)` adds `nopersist`, which makes the initramfs
  [ignore the persistence store](091-initramfs-init.md#overlay-root).
- `KDOS Live (verbose)` passes `loglevel=7`, every kernel message.

All three name `console=tty0` and then `console=ttyS0`. The last one is `/dev/console`, so the
initramfs prints to the serial port while the splash has the screen. `root=/dev/ram0` is not a
`root=UUID=`, so the initramfs takes the live path. The `timeout: 0` trap the comment names is
Limine's documented meaning of 0: boot at once and draw no menu.

### memtest86+

<!-- kfs:include script/phases/70_image/110_iso.sh lines=342-368 pin=de4885ba1073 -->

When [memtest86plus](#port-memtest86plus) is installed, its EFI program is copied to
`boot/memtest.efi` and an entry is added that starts it with `protocol: efi`. `if_fw_type: UEFI`
hides the entry on a BIOS boot. Without the package the menu has three entries.

## xorriso

<!-- kfs:include script/phases/70_image/110_iso.sh lines=370-415 pin=a70c6400235e -->

xorriso, from [libisoburn](#port-libisoburn), writes the image. Run as `xorriso -as mkisofs`, it
takes mkisofs's options:

`-iso-level 3`
: The ISO9660 level that lets a file be larger than 4 GiB − 1, which the two lower levels do not.

`-full-iso9660-filenames`
: Allow ISO9660 names of up to 31 characters. xorrisofs writes Rock Ridge records by default, and
  those carry the full names.

`-volid "KDOS_LIVE"`
: The volume label.

`-b boot/limine/limine-bios-cd.bin -no-emul-boot -boot-load-size 4 -boot-info-table`
: The BIOS entry in the El Torito boot catalogue: the boot image, marked as emulating no floppy or
  disk, with 4 sectors of 512 bytes loaded at boot, and with xorriso writing the block address of
  the volume descriptor, the block address of the image, its size and a checksum into bytes 8 to
  63 of it.

`--efi-boot boot/limine/limine-uefi-cd.bin`
: A second El Torito entry, for EFI, with the UEFI boot image.

`-efi-boot-part --efi-boot-image`
: List that same UEFI boot image in a [GPT]{.idx} as an EFI System Partition, which is where firmware
  booting a stick looks.

`--protective-msdos-label`
: Write an MBR partition table whose one partition covers the image but its first block.

These are the options Limine's `USAGE.md` gives for an ISO, with differences: KDOS adds the level,
the long names and the label, and does not pass the `-R -r -J -hfsplus -apm-block-size 2048` of
Limine's line.

`limine bios-install` then writes Limine's BIOS boot code into the first sector of the finished
image. Finding a GPT on an ISO image, it converts the table to MBR, and says so in the step's
output. The comment at the top of the block explains the layout: the ESP is the El Torito image
itself, inside the ISO9660 volume, and ISO9660 starts at sector 0, which is what lets the initramfs
find the medium by mounting the whole disk.

## The checks

<!-- kfs:include script/phases/70_image/110_iso.sh lines=417-457 pin=4467942a2c0d -->

Three properties of the finished image are tested, and any one missing stops the step after all
three have been reported:

1. `fdisk -l` from [util-linux](#port-util-linux) lists an EFI partition, under either of the two
   names fdisk gives it: `EFI System` in a GPT, `EFI (FAT-12/16/32)` in the MBR
   `limine bios-install` converts it to.
2. Bytes 510 and 511 are `55 aa`, the MBR signature.
3. The first 440 bytes, the MBR's boot code area, are not all zero, which shows that
   `limine bios-install` ran; xorriso writes the signature in item 2 either way. `od -v` is needed
   for this test, because without it `od` prints a run of identical lines as one `*`.

`testing/preflight.sh` checks the same boot structure without building, by looking for each of the
flags in this script.

## Booting the result

```bash
make run
```

boots `build/iso-build/kdos.iso` in QEMU with UEFI firmware and software graphics, with a disk to
install to, `build/kdos.qcow2`, which it creates empty when there is none. `make run-hw`
boots it with GPU acceleration, in a container. [Testing](../../kdos/05-developer/testing.md)
describes the rig that photographs a booted image.

## Reproducing an image

A package built twice from one tree is byte-identical, which
[Reproducible packages](../../kdos/03-architecture/packaging.md#reproducible-packages) explains. The
image phase does part of the same work for the image, and leaves some of it undone.

### What the scripts pin

`phase.env` sources `script/env/chroot.env`, which sources `script/env/common.env`, so every step of
this phase runs with a fixed `SOURCE_DATE_EPOCH` and `TZ=UTC`:

<!-- kfs:include script/env/common.env lines=18-32 pin=03a1ebb0a106 -->

`chroot.env` then sets `LC_ALL=C.UTF-8` over the `C` shown here; the sorts that order the initramfs
archives set `LC_ALL=C` on the command itself.

Three tools put times into the image, and each treats the epoch differently:

- mksquashfs sets the image's creation time to it, and every file time later than it is lowered to
  it. A file copied during the build therefore has the same time in `system.sfs` on every run.
- xorriso sets the volume's creation and modification dates and the GPT disk GUID from it. File
  dates on the ISO9660 volume are not touched: each file keeps the modification time it has on disk,
  and xorriso sets its access and change times to that.
- gzip does not read the epoch, but writes zero in its header's time field when it compresses a
  pipe, which is how the initramfs step runs it.

The initramfs and microcode archives list their files in byte order, and cpio's `--reproducible`
keeps the numbers of the devices the files are stored on out of them and numbers the inodes in
archive order from 0
([Packing](090-initramfs.md#packing)). The commit the image is built from reaches it only through
`KDOS_GIT_COMMIT`, `KDOS_GIT_DIRTY`, `KDOS_GIT_DATE` and `KDOS_GIT_TIME`, which the `Makefile` reads
from git on the host. `045_identity.sh` ([its chapter](045-identity.md)) writes the commit and its
date into `/etc/os-release`, never the time of the build, and `105_ports.sh` writes the commit and
its time into `/ports/TREE`.

### What still differs between two builds

Two runs of the image phase over the same root do not give the same bytes:

- **File times in the initramfs.** Every file in `build/initramfs` is a fresh copy made by the step,
  so it has the time of the run, and cpio stores each file's modification time. The initramfs
  differs, and so does `system.sfs`, which holds a copy of it in `/boot`.
- **File times on the ISO9660 volume.** `vmlinuz`, `initramfs.cpio.gz`, `system.sfs`, the Limine
  files, the font, the backdrop and `limine.conf` are all written or copied into `build/iso_root` by
  the step, and xorriso records the time each was written.
- **The sources stamp.** With `KDOS_ISO_SOURCES=1`, `sources/SOURCES` has a `built` line with the
  time of the copy.

Two more inputs change the image whenever they change. A rebuilt `linux` package has different
module signatures (see the same
[Reproducible packages](../../kdos/03-architecture/packaging.md#reproducible-packages) section), and
the initramfs carries modules. And xorriso writes its own version and build date into the volume's
Preparer Id field, so a different xorriso gives a different image from the same files.

### Building the same image again

To come as close as the scripts allow, rebuild from the same clean commit, so that `KDOS_GIT_DIRTY`
is 0, with the same make variables: `KDOS_ISO_COMP`, `KDOS_PACK_KDOS`, `KDOS_ISO_SOURCES` and
`KDOS_MAKE_BINHOST`. `build/keys/kdos-release.pub`, which `105_ports.sh` installs into the image
when it exists, is not in git, so both builds need the same key, or neither.

Because the times above differ, two such images are compared by what they hold rather than byte for
byte. The volume's own dates come from the epoch:

```bash
xorriso -indev build/iso-build/kdos.iso -pvd_info
```

prints the epoch's date and time as both `Creation Time` and `Modif. Time`, and the xorriso that
made the image as its `Preparer Id`. To compare what two images hold rather than
their bytes, extract each one and compare the trees:

```bash
xorriso -osirrox on -indev a.iso -extract / a
xorriso -osirrox on -indev b.iso -extract / b
diff -r a b
```

`unsquashfs -s a/system.sfs` prints the image's creation time, which is the epoch, and
`unsquashfs -lls` lists every file in it with its time.
