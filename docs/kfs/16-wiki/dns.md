# DNS

This page covers how a KDOS machine turns names into addresses: the caching resolver
NetworkManager runs on the loopback address, the single writer of [`/etc/resolv.conf`]{.idx}, the files
involved, and how to see and change which servers answer. The mechanism is described once in
[Networking](../../kdos/02-user-guide/administration.md#networking); this page is the procedures.

## Installation

Four ports take part, all in the `network` shelf's list of `41_system` and all on every image:

- [dnsmasq](#port-dnsmasq), the [caching resolver]{.idx} NetworkManager starts on `127.0.0.1`
  and `::1`. NetworkManager runs a second [`dnsmasq`]{.idx} of its own for each
  [hotspot](access-point.md);
- [openresolv](#port-openresolv), whose [`resolvconf`]{.idx} is the one program that writes
  `/etc/resolv.conf`;
- [networkmanager](#port-networkmanager), which feeds the resolver each connection's servers;
- [ldns](#port-ldns), whose `drill` is the tool for asking a [DNS]{.idx} server a question directly.

Programs on KDOS resolve names through musl's resolver, which reads [`/etc/hosts`]{.idx} and the servers in
`/etc/resolv.conf`. There is no service script for DNS: the resolver starts and stops with
NetworkManager (see [NetworkManager](networkmanager.md)), and on a machine where NetworkManager is
disabled [`dhcpcd`]{.idx} hands the servers it is given to `resolvconf` directly.

## Configuration

### `/etc/resolv.conf`

The file the image ships, from `fs/`:

<!-- kfs:include fs/etc/resolv.conf -->

`resolvconf` replaces it as soon as a link comes up. It does so only because the first line is
its signature, `# Generated by resolvconf`: given a file that starts with anything else,
`resolvconf -a` prints *signature mismatch: /etc/resolv.conf* and fails, NetworkManager carries on
with the file as it was, and `wg-quick` takes its tunnel down again. While NetworkManager runs,
the result names only `127.0.0.1`, the local `dnsmasq`, even when `dhcpcd` has handed
`resolvconf` servers of its own: `resolvconf` writes only the local resolver when one of the
entries names it. The installer copies the live system's copy to the disk
(see [What the installer writes](../../kdos/02-user-guide/installation.md#what-the-installer-writes)).

### `resolvconf`

<!-- kfs:include ports/core/network/openresolv/build.sh lines=12-16 pin=09c9d19b36e4 -->

`SUBSCRIBERS` names the programs `resolvconf` can pass the merged result to; `libc` is the one
that writes `/etc/resolv.conf`. The package also installs upstream's [`/etc/resolvconf.conf`]{.idx}, whose
`resolv_conf` line names that file; `resolvconf.conf(5)` lists the other keys. Each program that
brings a link up hands `resolvconf` the servers for that link under a name of its own, which
`resolvconf -i` lists, and `resolvconf` merges them, so none of them overwrites another's
entries.

### NetworkManager's resolver

<!-- kfs:include ports/core/network/networkmanager/build.sh lines=64-69 pin=954e879afefd -->

`dns=dnsmasq` makes NetworkManager start `dnsmasq` listening on `127.0.0.1` and `::1`, give it
each active connection's servers, and write `127.0.0.1` to `/etc/resolv.conf` through
`resolvconf` (the port names `/usr/sbin/resolvconf` at build time).

The local resolver splits names by domain. Each connection's servers are asked about the domains in
that connection's search list; a name in no connection's list goes to the servers of the
connections that hold the default route. A [VPN]{.idx} that carries only its own networks is therefore
asked only about its own domains, and one that takes the default route is asked about everything
else as well. The rules, and the `ipv4.dns-priority` property that orders them, are in
`nm-settings-nmcli(5)`.

NetworkManager starts this `dnsmasq` with `--no-hosts`, so the
local resolver itself does not read `/etc/hosts`; programs on this machine still see
`/etc/hosts`, because the C library reads it before it asks a server.

`dnsmasq` also reads every file in [`/etc/NetworkManager/dnsmasq.d/`]{.idx term="/etc/NetworkManager/dnsmasq.d"}
(its `--conf-dir`), which the image ships empty. That is where an option of your own goes, such as a server for one domain
(`server=/<domain>/<address>`); `dnsmasq(8)` lists the options.

### `/etc/hosts`

<!-- kfs:include fs/etc/hosts -->

The installer rewrites the `127.0.1.1` line with the host name you choose. Add a line of your own
for any name this machine should resolve without asking a server.

## Usage

### Seeing which servers are in use

1. Read what the C library uses:

   ```bash
   cat /etc/resolv.conf
   ```

   `# Generated by resolvconf`, then `nameserver 127.0.0.1` and `options edns0 trust-ad`, means
   NetworkManager's resolver is in charge.

2. See the servers each link handed to `resolvconf`, each under a heading such as
   `# resolv.conf from NetworkManager`, and the names they are kept under:

   ```bash
   resolvconf -l
   resolvconf -i
   ```

   NetworkManager's own entry names `127.0.0.1`; `dhcpcd`'s is `eth0.dhcp` (for `eth0`), and a
   `wg-quick` tunnel's is the tunnel's interface name.

3. See the servers NetworkManager gave the resolver for one device:

   ```bash
   nmcli -f IP4.DNS,IP6.DNS,IP4.DOMAIN device show <interface>
   ```

### Asking a question

```bash
getent hosts example.org             # through the C library, as every program asks
drill example.org                     # the servers in /etc/resolv.conf, with the full answer
drill @9.9.9.9 example.org            # one server, by-passing the local resolver
```

When `getent` fails and `drill @<server>` answers, the fault is between this machine and its
resolver, not in the outside world.

### Choosing the servers for a connection

1. Set the servers on the profile and tell NetworkManager to ignore the ones DHCP offers:

   ```bash
   nmcli connection modify "<profile>" ipv4.dns "9.9.9.9 149.112.112.112" ipv4.ignore-auto-dns yes
   ```

   Use `ipv6.dns` and `ipv6.ignore-auto-dns` for IPv6.

2. Bring the profile up again so the resolver gets the new list:

   ```bash
   nmcli connection up "<profile>"
   ```

### Adding a `dnsmasq` option

1. Write the option into a file of your own:

   ```bash
   sudo mkdir -p /etc/NetworkManager/dnsmasq.d
   echo 'server=/corp.example/10.0.0.53' | sudo tee /etc/NetworkManager/dnsmasq.d/50-local.conf
   ```

2. Restart the resolver. This interrupts name resolution for a moment:

   ```bash
   sudo nmcli general reload dns-full
   ```

`reload` is one of the NetworkManager actions the polkit rule leaves out, so it needs `sudo`.

### Running without the local resolver

To have NetworkManager hand each connection's servers to `resolvconf` directly, with no `dnsmasq`
in between, override the port's file with one of the same name:

```bash
printf '[main]\ndns=default\n' | sudo tee /etc/NetworkManager/conf.d/10-kdos-dns.conf
```

and restart NetworkManager as [Restarting the daemon](networkmanager.md#restarting-the-daemon)
shows; a plain `service restart` in a desktop session leaves the old daemon, and the old
setting, running. `/etc/resolv.conf` then names the connection's own servers, and
`pgrep -a dnsmasq` shows only libvirt's.

Without the local resolver, NetworkManager hands every active connection's servers to
`resolvconf` in one list, ordered by `ipv4.dns-priority`, and nothing splits names by domain: the C
library asks the first server about every name, a VPN's included. Delete the file and restart
NetworkManager to return to the shipped arrangement.

### On the live medium and on an installed system

The two behave the same. On the live medium a file you add under `/etc` lasts until the next
reboot unless the medium has a persistence store.

## Tips

- `kdos why /etc/resolv.conf` reports the file as provided by `fs/`, not by a package: the copy
  in the image is the placeholder above, and `resolvconf` writes the one in use.
- `sudo resolvconf -u` rebuilds `/etc/resolv.conf` from what the links last handed it, which is
  what to run after editing `/etc/resolvconf.conf`. It, and every `wg-quick up` and `down`,
  prints `Usage: service nscd <name>`: after each update `resolvconf` tries to restart `nscd`
  with `service nscd`, which is not the order KDOS's `service` takes (`resolvconf -R` prints the
  command). No `nscd` is installed, so nothing is lost.
- A `.local` name is mDNS, answered by Avahi rather than by a DNS server; `avahi-resolve -n
  <name>.local` looks one up.
- After changing the host name, change the `127.0.1.1` line of `/etc/hosts` to match. The C
  library finds the machine's own name only there; without it the name goes to the DNS, which
  answers that it does not exist when the machine is online and times out when it is not.
- `drill -S` checks a DNSSEC chain, and needs a trust anchor given with `-k`; none is installed
  (see [Known gaps](#known-gaps)).

## Troubleshooting

**Addresses work and names do not.**
`cat /etc/resolv.conf`. If it holds only the shipped `nameserver 127.0.0.1` line and nothing
answers there, the resolver is not running: check `service status networkmanager` and
`pgrep -a dnsmasq`. NetworkManager's `dnsmasq` is the one with `--listen-address=127.0.0.1`; the
two started with `--conf-file=/var/lib/libvirt/dnsmasq/default.conf` serve libvirt's `virbr0`
network. With NetworkManager disabled on purpose, `service status network` should show
`dhcpcd`, and `resolvconf -l` should list the servers it was given.

**Names fail just after boot and work a moment later.**
The shipped file names only this machine, and nothing answers on `127.0.0.1` until NetworkManager
has started its `dnsmasq`. A lookup made before the network is up fails at once instead of
reaching an outside server, as the comment in the file says.

**Names fail after a VPN goes down.**
`resolvconf -i` lists the names entries are kept under, and `resolvconf -l` shows each entry, so
a tunnel's that outlived the tunnel is visible. `sudo resolvconf -d <name>` removes it;
`sudo resolvconf -u` rewrites the file.

**A `dnsmasq` of your own will not start, saying port 53 is in use.**
NetworkManager's resolver holds port 53 on `127.0.0.1` and `::1`, and libvirt's on
`192.168.122.1`. Give your `dnsmasq`
`bind-interfaces` and an `interface=` line, so it binds only where it serves; see
[Serving a network with hostapd](access-point.md#serving-a-network-with-hostapd).

**One domain resolves wrongly on a VPN.**
`nmcli -f IP4.DNS,IP4.DOMAIN device show <tunnel>` shows the servers and the domains the tunnel
gave the resolver. A domain that is missing there is not sent to the tunnel's servers, unless the
tunnel holds the default route. Add it to the profile with
`nmcli connection modify "<profile>" ipv4.dns-search <domain>` and bring the profile up again.
